# 中间环节「生成户型」方法选型

> 目标：在 [① 建筑边界 + 结构约束（柱/墙/核心筒）] 与 [③ AdaptiveReuseEnv (MAPPO 移动)] 之间，
> 补上一步自动生成初始户型，产出 `TargetSpaces[].initial_rect` + `seed`，并保证生成结果
> 硬合法（不越界、不侵入结构、不重叠、满足面积/形态/邻接约束）。

## 0. 先厘清问题：为什么这一步是必需的

现状实测（`core/seed_growth/geometry.py` 当生成器跑一次，retrofit 案例）：

| 指标 | 结果 |
|---|---|
| 耗时 | 0.66 s |
| 六房间面积误差 | 0.00（全部命中目标） |
| 矩形度 | 1.000 |
| 几何硬错误 | 0 |
| **四条 adjacent 关系** | **全部失败，shared_length = 0** |

根因：该解码器是**各房间从自己的种子独立四向扩张**，房间之间只会互相「推开」，
不会贴合成共边。所以它得到的是「面积正确的一堆散块」，不是**可居住的户型**。

**结论：缺的不只是一个 initial_rect 生成器，而是「带邻接/拓扑约束的空间划分器」。**
这一点决定了方法选型的走向 —— 必须选**能显式表达拓扑关系**的方法，
而不是单纯「把多边形塞进边界」的方法。

## 1. 方法全景（按与本项目的契合度排序）

### 路线 A：拓扑树骨架 + 矩形划分（推荐，工作量最小）

即经典「slice-and-dice / squarified treemap（平方化树图）/ 切片树」方法。

**核心思路**：把户型当作一棵**拓扑树**——
客厅是根，走廊/交通核是中间节点，卧室/厨卫是叶子。
先在拓扑树上递归地把自由区域**二分切分**，每切一刀沿水平或竖直方向，
切分比例由子树的面积需求决定。因为每刀都是「整块切开」，
相邻房间**天然共享一条整边** —— 邻接关系自动满足，不需要事后修补。

- 面积需求 → 切分比例：直接映射，误差可控。
- 邻接关系 → 拓扑树结构：相邻即兄弟节点或父子节点。
- 长宽比 → 切分时约束单边长度上下限（squarified 变体专门优化这一点）。
- 结构约束（柱/墙/核心筒）→ 作为**子区域的硬空洞**参与可用面积扣除；
  柱子落在切分线上的情况少见，落在房间内部时按「房间带洞」处理或触发重切。

**优点**
- 零训练成本，毫秒级出结果，确定性可复现。
- 邻接**由构造保证**，这是它相对现有解码器的决定性优势。
- 与项目现有栈完全兼容：只需要 `shapely` + `numpy`，**无需新依赖**。
- 实现量：约 300–500 行 Python，可独立成 `core/layout_gen/slicing.py`。

**缺点与对策**
- 只能产矩形（或 L/T 形）。对「斜墙贴合」「非矩形凹口」无能为力。
  → 对策：作为**第一阶段粗布局**，把斜墙/凹口留给已有的 `edge_growth.py`（A/B 斜边）做精化。
    这条路径和项目 CP3→CP4 的分层设计完全一致，复用现有代码。
- 拓扑树需要指定。可以用启发式生成（客厅居中、卧室按面积降序、厨卫贴边），
  或从 `FunctionalRelations` 反推（adjacent 边建树、separate 边加约束）。

**本项目落地方式**：
```
自由区域 (shapely Polygon)
  ├─ 扣除核心筒/交通核 → 剩余可用区域
  ├─ 按 FunctionalRelations 构造拓扑树（adjacent 连边、separate 排斥）
  ├─ squarified 递归切分 → 每个房间一个矩形
  └─ 输出 initial_rect 列表 → 回写 YAML
```

### 路线 B：约束满足 / 优化求解（质量最高，成本最高）

把「生成户型」写成一个**可行性问题**，交给求解器：

- **变量**：每个房间的 `x1,y1,x2,y2`（连续坐标）
- **硬约束**：边界包含、结构不侵入、房间不重叠、面积上下限、长宽比上下限
- **软目标**：邻接共边长度最大化、与原始户型复用率最大化、改造量最小化

可选求解器：
- **CP-SAT（OR-Tools）**：把坐标离散化到 0.1m 网格，用整数变量建模。
  邻接共边可以表达为布尔变量组合，是这类「矩形排布」问题的成熟做法。
- **MINLP / 序列二次规划**：连续变量版，但非凸，容易陷入局部解。
- **遗传算法 / 模拟退火**：编码房间顺序 + 切分方向序列，直接在路线 A 的参数空间里搜索。

**优点**：理论上能找到全局更优、邻接全覆盖的解；可以加任意复杂约束。
**缺点**：
- OR-Tools 需要新增依赖（项目当前没有）；建模与调参成本高。
- 连续非凸问题**不保证**得到可行解，需要设计回退。
- 求解时间从毫秒级跌到秒级甚至分钟级，不适合放在训练循环内。

**适用场景**：离线批量生成候选布局库，或对最终交付方案做精修。
不建议作为主路径。

---

### 路线 C：预训练生成模型（最前沿，工程量最大）

- **扩散模型 / GAN**：在大量真实户型数据集上训练，直接采样户型。
  代表工作如 HouseDiffusion、House-GAN++（本项目 `FreeLayout Masklayout Text2plan/`
  目录下已有相关素材，值得先摸一遍）。
- **自回归序列模型**：把户型表示成房间序列 + 位置 token，逐个生成（HouseDiffusion 就是这个范式）。
- **条件 VAE / 图神经网络**：以边界 + 结构为条件，生成房间划分。

**优点**：能学到真实户型的先验（朝向习惯、动静分区、面积配比），生成结果「像人设计的」。
**缺点**：
- 需要**大规模户型数据集**和**训练算力**，项目目前没有这个基础。
- 生成结果**不保证硬约束满足**，必须配一个约束投影/后处理步骤（回到路线 A 或 B）。
- 泛化到「结构约束下的既有建筑改造」这种特定场景，公开预训练模型基本不可直接用。

**适用场景**：中长期研究方向，不是当前要补的那个环节的最快解法。

---

### 路线 D：启发式 / 规则驱动（最快能跑通，质量中等）

按建筑常识写规则，直接拼装：

- 客厅占据朝向最好的区域（南向 / 主立面）。
- 卧室、厨卫沿客厅周边依次排布，按面积降序。
- 卫生间贴近卧室，厨房贴近餐厅与外墙。
- 交通核作为固定块先扣除。

实现上可以看成「手工版的拓扑树切分」，比路线 A 灵活但没有通用性。
如果只是想让 pipeline **先跑通、出图、能看**，这条最快（1 天内）。

**缺点**：每换一个建筑就要改规则；无法处理复杂边界。

## 2. 推荐组合：A 打底 + CP4 精化（复用现有代码）

这是与本项目契合度最高的方案，而且**几乎没有沉没成本**：

```
阶段 1  拓扑树 + squarified 矩形切分        ← 新增 ~400 行，shapely 原生
阶段 2  结构约束投影（柱子/核心筒挖空）      ← 复用 structure_geometry.py
阶段 3  斜墙/凹口精化（可选）                ← 直接复用 edge_growth.py 的 A/B 逻辑
阶段 4  硬验收                              ← 直接复用 validation.py
阶段 5  输出 initial_rect + seed → YAML
```

**为什么这个组合特别合适**：
- 阶段 4 的 `validation.py` 已经写好了（边界/结构/重叠/面积/形态/邻接共边全部有检查），
  不用重写验收标准。
- 阶段 3 的 `edge_growth.py` 已经实现了斜墙 A/B 贴合，正是矩形切分之后需要的能力。
- 阶段 2 的 `structure_geometry.py` 已提供含厚度的固定构件多边形。
- 整条链只需要 `shapely` + `numpy`，**不加任何依赖**，与 `communitymarl` 环境现状一致。

**关键要改的一点**：现有 `geometry.py` 的扩张式生长要**替换为切分式**。
扩张式天生无法产生共边邻接（已被实测证实），切分式天然产生共边。

## 3. 各方法对比

| 维度 | A 拓扑树切分 | B 约束求解 | C 生成模型 | D 规则启发式 |
|---|---|---|---|---|
| 邻接保证 | 构造保证 ✓ | 优化目标 | 不保证 | 构造保证 ✓ |
| 完成工作量 | 中（400 行） | 大 | 很大 | 小（1 天） |
| 新依赖 | 无 | OR-Tools | torch + 数据集 | 无 |
| 出解速度 | 毫秒 | 秒～分钟 | 秒（GPU） | 毫秒 |
| 确定性 | 是 | 是（CP-SAT） | 否 | 是 |
| 非矩形/斜墙 | 需配合 CP4 | 可建模 | 天然支持 | 差 |
| 泛化到新建筑 | 好 | 好 | 需重训 | 差 |
| 与项目现有栈契合 | **最高** | 中 | 低 | 中 |

## 4. 对「强化学习方案」的补充说明

你在对话里已经讨论过 RL 方案（用 RL 学一个户型生成策略）。补充几点判断：

1. **RL 与路线 A 不冲突，是叠加关系。**
   路线 A 可以作为 RL 的 **动作空间载体**：让智能体选择「切分点位置」而不是「像素级移动」，
   搜索空间瞬间收窄，样本效率会高很多。这比让 RL 从零学几何要现实。

2. **本项目已有两套 RL，要避免重复造轮子。**
   - `AdaptiveReuseEnv` + MAPPO：智能体移动房间矩形（**这已经是你要的第四步**）。
   - `core/seed_growth` + 独立 5 动作环境：智能体移动**种子点**，再离线精确生长。

   如果中间层也用 RL，会出现**三层 RL 串联**，训练难度和调试成本陡增。
   建议：中间层用**非学习**方法（A 或 D），把 RL 留给第四步的空间精调。

3. **RL 的真正价值点在「多目标权衡」。**
   如果你希望系统自动权衡「面积合规 vs 邻接质量 vs 改造量 vs 结构对齐」，
   这类没有唯一正确答案的偏好问题，RL 或进化算法比确定性切分更有发挥空间。

## 5. 建议的下一步

1. **先做路线 A 的最小可用版**：只处理矩形边界 + 规则拓扑树，
   目标是在 retrofit 案例上产出 `shared_length > 0` 的四条邻接。
2. **复用 `validation.py` 验收**，把「邻接是否满足」作为第一验收指标
   （面积和形态现有解码器已能达标，瓶颈就是邻接）。
3. **接入 YAML**：新增 `scripts/generate_layout.py`，
   读 `config/retrofit/config.yaml` → 生成 → 写回 `TargetSpaces[].initial_rect` 与 `seed`。
4. **再评估是否需要路线 B 精修**：如果路线 A 的邻接覆盖已经够好，就不必引入求解器。
